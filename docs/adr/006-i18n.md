# ADR 006. i18n: a localizable string is a value the widget holds

- **Status:** **Accepted and implemented**, revision 2. §2.4 (Spinner's locale-aware number
  entry) was deliberately left out of the first delivery and delivered on 2026-09-27; §9
  records what implementing settled, and §9.1 what the Spinner work settled, including where
  it departs from §2.4's text. Revision 1 put the English at the call site behind a
  `tr(key, fallback)` lookup resolved at measure/paint time. It is recorded here because
  the reason it was replaced is the whole argument for what follows: `tr` made *not
  capturing its result* a rule that nothing could enforce, and the toolkit's own
  `SearchField` was already breaking it (§0, finding 5). Revision 2 makes the localizable
  string a **type** (one the component stores instead of a `String`), so capturing it is
  the default rather than the bug.
- **Date:** 2026-08-01
- **Scope:** how Limn's built-in strings become localizable, where the UI locale lives, how
  an application supplies many translation files, and which locale-sensitive behaviors
  (number/time entry) change. Rendering of new scripts is scoped, not solved (§4).
- **Audience:** whoever implements it. Every claim below is tied to a file:line in this
  repo, or explicitly marked as unverified/judgement.

---

## 0. The five findings that decide the shape of this work

**Finding 1: the localizable string surface is tiny, and that changes what kind of
project this is.** An exhaustive sweep of all three library modules found roughly twenty
user-visible literals, almost all in `limn-components`: SearchField's `"Search…"`
placeholder (`SearchField.java:22`), Viewport3D's `"3D unavailable (no GPU backend)"`
(`Viewport3D.java:256`), ColorPicker's channel letters and format-tab captions (the tabs
are `Format.name()` used as UI text: `ColorPicker.java:191`, letters at `:989-991`), the
thirteen `Theme` display names exposed through the public `name` field (`Theme.java:158-194`),
and the backend's `"Display " + (index + 1)` monitor fallback (`LwjglDisplay.java:53`).
Everything else is out by construction: Dialog ships no button captions (`Dialog.java:212`;
text is always caller-supplied), TextField/TextArea have no context menu, ComboBox cannot
be empty, and the native file dialogs pass through only caller strings while the OS
localizes its own Open/Cancel chrome (`TinyFdDialogs.java:35-37`; `Filter.description` is
the caller's, `FileDialogs.java:29`). Crash and error text is logs and exceptions:
developer-facing, out of scope. So i18n v1 is **not a string-extraction epic** for this
repo; the mechanism exists mostly for the applications built on it, which is why §1 is
designed around an app with fifty screens rather than around these twenty strings.

**Finding 2: the real debt is formats, not strings.** The repo has zero locale
infrastructure: no `NumberFormat`, `Collator`, `MessageFormat`, `ResourceBundle` or
`java.text.Bidi` anywhere in main sources; every `Locale` use is a deliberate ROOT/US pin.
A place for the UI locale to live must be invented. The hot spot is Spinner: display pinned
to `Locale.US` (`Spinner.java:267,269`), an ASCII-only input regex (`:106`), a comma
tolerated on parse only when no period is present (`:446`, so de-DE `1.234` silently
misreads as 1.234 instead of 1234), an ASCII-digit keystroke gate (`:453`), and a
silent-drop commit on any parse failure (`:392`). Three inconsistent digit policies coexist
in one widget (typed vs pasted vs time-mode). A pt-BR or de-DE user cannot enter their own
decimal separator and is never told why. **Formats are not strings and do not go in a
table**, which is why §1 gives them the same epoch and a different payload.

**Finding 3: the propagation machinery already exists, and Theme shows the anti-pattern
to avoid.** A language switch is measurement-affecting exactly like a font switch. Fonts and
ControlSize already solve that: a process-wide static registry with a copy-on-write listener
list (`Fonts.java:57,67`; `ControlSize.java:112-123`), an epoch bump for widget-private
caches (`Widget.bumpControlSizeEpoch()` at `ControlSize.java:119`), and every Scene
subscribing in its constructor through the weak `GlobalMetricsListener`
(`Scene.java:218-219,246`) which funnels into `Scene.relayout()` (`:293`), overlays and
unbound scenes included. Theme is the counterexample the repo itself documents:
`setCurrent` assigns a volatile and notifies nobody (`Theme.java:250`), pushing manual
`markNeedsLayout()` onto app code (`Theme.java:17-18`), and Theme's own javadoc names routing
through the Fonts/ControlSize registry as the sanctioned upgrade path (`Theme.java:236-239`).
This ADR copies Fonts, not Theme.

**Finding 4: what "more languages" can even render today draws the honest v1 boundary.**
Latin, Greek, Cyrillic (Roboto, 4 styles), pan-CJK and monochrome emoji work end-to-end:
per-code-point fallback (`FontStore.java:445`; chain faces parsed in the background at
`:187`, installed at `:232`), background "curing" of late-loaded faces
(`FontStore.java:124-129`), full IME preedit into TextField and TextArea, grapheme-cluster-safe
editing (`\X` in TextEditModel). Arabic, Hebrew, Indic and Thai are structurally blocked one
layer lower: the atlas is keyed by code point (`GlyphAtlas.java:109`), there is no GSUB/GPOS
shaping, no bidi stage, and caret/selection math assumes monotone LTR prefix widths
(`TextField.java:289`). Shipping an Arabic string table before shaping exists would render
*wrong text*, worse than `.notdef`. So v1 targets locales the pipeline can draw (LGC + CJK:
pt, de, fr, es, it, ja, ko, zh, ru, el…), and the string type is deliberately orthogonal
to text direction so nothing here is redone when shaping lands (§4).

**Finding 5: a resolve-at-use function cannot be made safe, and this repo already proves
it.** Revision 1's rule was "never store the result of `tr()` in a field". The failure it
guards against is silent: one widget keeps yesterday's language after a switch, everything
around it changes, and no test catches it because tests do not switch locales. The rule is
unenforceable by construction, since `checkArchitecture` scans imports (`build.gradle.kts:70`),
not data flow; and the toolkit contains a live instance of the trap before the feature even
exists: `SearchField` sets its placeholder in its constructor (`SearchField.java:22`) into a
`String` field that `TextField` requires non-null (`TextField.java:46,100`), so revision 1
had to invent a per-widget "did the app override it" flag to work around a rule it could not
enforce. **The same widget under revision 2 needs no flag at all** (§2.3): the field holds
the localizable value, and replacing it with the app's own is an ordinary assignment.
A type does structurally what a convention was asking people to remember.

## 1. Decision

1. **`I18nString` is a value type in `limn-toolkit`** (package `limn.i18n`), constructed as
   `new I18nString("limn.searchField.placeholder", "Search…")`: a key, and the English that
   is simultaneously the fallback and the source of truth for the default language. It
   caches its resolved text **in the instance**, validated against a global epoch: the
   memo shape `Widget.controlSize()` already uses (`Widget.java:68,81,486-492`).
2. **A text-bearing component stores one `I18nString` field, never a `String`.** The
   existing `setText(String)` overloads survive by wrapping the literal
   (`I18nString.literal`), so there is exactly one field, one source of truth, and no
   precedence question between the two setters; the last call wins because there is only
   one place to win. `String text()` keeps its signature and returns the resolved text, so
   no existing caller changes.
3. **Updates arrive automatically and without per-string bookkeeping.** A locale or bundle
   change bumps the epoch and notifies; every Scene relayouts; each widget's next measure
   reads its `I18nString`, sees a stale epoch and re-resolves. No listener per string:
   an application with ten thousand localizable strings registers nothing and leaks
   nothing.
4. **Many files, by design.** A real screen has dozens of keys and an application has
   dozens of screens, so bundles are per-file and any number may be registered;
   `StringBundle.prepare(Locale)` is called at the switch so file I/O never lands in a
   measure pass.
5. **The key catalog is a runtime fact, not a document.** Every keyed `I18nString`
   registers its (key, English) pair on construction, so `I18n.declaredKeys()` *is* the
   catalog; a test asserts a bundle covers it, and a tool dumps a starter file for
   translators. Revision 1's hand-maintained `docs/i18n-keys.md`, which was its own
   admitted weakness, does not exist.
6. **Humans get `I18n.locale()`, machines keep `Locale.ROOT`/`US`.** Spinner's number entry
   becomes locale-aware against the same epoch; hex stays hex; font-family keying, glob
   patterns and os.name probes stay pinned (and the two naked `toLowerCase()` calls at
   `LwjglBackend.java:115` and `LwjglWindow.java:1200` get the `Locale.ROOT` the rest of the
   repo already uses).

### 1.1 The type

```java
public final class I18nString {                    // limn.i18n.I18nString

    public I18nString(String key, String english);  // both non-null; registers the pair
    public static I18nString literal(String text);  // no key: resolves to itself, forever
    public static final I18nString EMPTY;           // literal("")

    public String get();                            // resolved; epoch-validated cache
    public String format(Object... args);           // MessageFormat under I18n.locale()
    public String key();                            // null for a literal
    public String english();
    public boolean isLiteral();

    @Override public String toString();             // == get(), so logging reads right
    // equals/hashCode on (key, english): two literals of the same text are the same value
}
```

The cache is three fields and no allocation:

```java
private final String key, english;
private String cached;
private long cachedEpoch;                 // 0 = never resolved; I18n.epoch() starts at 1

public String get() {
    long epoch = I18n.epoch();
    if (cachedEpoch != epoch) {           // Widget.controlSize()'s memo, verbatim
        cached = key == null ? english : I18n.resolve(key, english);
        cachedEpoch = epoch;
    }
    return cached;
}
```

UI thread only, like every other mutable state in the toolkit. The epoch is a plain
`long` for the same reason `controlSizeEpoch` is (`Widget.java:60-68`): the worst case of a
missed bump is a *stale read*, never a wrong resolution, and a global counter is cheaper
than precise invalidation.

**A component's strings are `static final`,** so the cache is one slot per key for the whole
process rather than one per widget; a list with 500 rows of the same localized label
resolves once per language change, not 500 times.

### 1.2 The registry

```java
public final class I18n {                          // limn.i18n.I18n
    public static Locale locale();                 // starts at Locale.getDefault()
    public static void setLocale(Locale l);        // UI thread; prepare → bump → notify
    public static long epoch();

    public static void addBundle(StringBundle b);      // newest wins; prepares, bumps, notifies
    public static void removeBundle(StringBundle b);

    public static void addChangeListener(Runnable r);  // COW, addIfAbsent; Fonts.java:24,68
    public static void removeChangeListener(Runnable r);

    public static Map<String, String> declaredKeys();  // every keyed I18nString ever built
    static String resolve(String key, String english); // package-private: I18nString only
}

public interface StringBundle {                    // limn.i18n.StringBundle
    String lookup(String key, Locale locale);      // null = "not mine", the next bundle tries
    default void prepare(Locale locale) { }        // called before the notification
}
```

`setLocale` follows `ControlSize.setProcessDefault` (`ControlSize.java:112-123`) with one
step in front: `Ui.checkUiThread()`, no-op-if-equal, **`prepare` every bundle**, bump the
epoch, then notify.

### 1.3 Many files

```java
public final class PropertyBundle implements StringBundle {
    /** /i18n/settings_pt-BR.properties, then _pt, then the base file. UTF-8. */
    public static PropertyBundle family(String baseResourcePath);
    public static PropertyBundle family(String baseResourcePath, ClassLoader loader);
    public static PropertyBundle of(Locale l, Map<String, String> strings);
}
```

```java
I18n.addBundle(PropertyBundle.family("/i18n/common"));
I18n.addBundle(PropertyBundle.family("/i18n/settings"));
I18n.addBundle(PropertyBundle.family("/i18n/editor"));       // one per screen, as many as it takes
```

A `family` holds one loaded table per locale it has been prepared for; `lookup` is a single
hash get returning `null` on a miss, so N registered files cost N hash gets **once per
string per language change** and nothing at all afterwards; the epoch cache is what makes
"dozens of files" a non-question. `prepare` is where the classpath read happens, which is
why it exists: a lazy load would otherwise fire inside a measure pass, during the frame
that switches the language.

Keys are globally unique dotted strings, and the screen prefix is the convention that keeps
them so (`settings.title`, not `title`). No mounting, no per-bundle namespace: a bundle that
misses simply returns `null`, and one that answers a key it did not intend is a duplicate
key, which `declaredKeys()` makes visible.

### 1.4 Parameters and plurals

`format(Object... args)` runs `java.text.MessageFormat` under the current locale and is
**not** cached; arguments vary per call, and caching them would be caching the wrong thing.
Plain `get()` never touches MessageFormat, so an apostrophe in an unparameterized string
needs no escaping. Translations of parameterized keys are MessageFormat patterns
(apostrophes doubled); `format` catches a malformed pattern and returns the English one, so
a bad bundle cannot crash a paint. Numeric arguments are locale-formatted by MessageFormat,
so pass `Integer.toString(n)` where ASCII digits are required, as the one backend string
does (§2.5).

**No plural rules in v1.** The libraries ship no plural-bearing string, so the cost falls on
applications, and the documented workaround is separate keys chosen by application code.
A `one/other` signature would be the wrong shape for Slavic and Arabic, and adding
selection behind `format` later breaks nothing.

## 2. The work, file by file

### 2.1 `limn-toolkit`: `limn/i18n/` (new)

`I18nString`, `I18n`, `StringBundle`, `PropertyBundle`. No new dependency:
`java.util.Locale`, `java.util.Properties` and `java.text` are `java.base`, and the
architecture ban covers AWT/Swing/SWT and confined LWJGL only (`build.gradle.kts:52-57`).

### 2.2 `limn-toolkit`: `Scene.java`

Three lines, not one. The subscription joins the existing two (`Scene.java:218-219`):
`I18n.addChangeListener(metricsListener)`. And the weak wrapper's two maintenance sites
must learn the third registry too: the dead-scene cleanup branch (`Scene.java:256-258`) and
`bind()`'s repair block (`:277-280`) remove/re-add from I18n exactly as they do for Fonts
and ControlSize. Skipping that leaks: scenes are created per popup open
(`ComboBox.java:260`, `PopupMenu.java:410`, `Dialog.java:474`), so a subscription with no
cleanup grows the listener list for the process lifetime, which is the precise pinning the
weak-listener javadoc exists to prevent (`Scene.java:239-245`).

### 2.3 `limn-components`: the one-field conversion

Every text-bearing component turns its `String` field into an `I18nString` field. `Label`
(`Label.java:61,93,97`) is the pattern for all of them:

```java
private I18nString text = I18nString.EMPTY;

public Label setText(I18nString newText) {
    Ui.checkUiThread();
    Objects.requireNonNull(newText, "newText");
    if (text.equals(newText)) {
        return this;                       // unchanged: no layout, no damage
    }
    ...                                    // the existing same-size fast path, verbatim
}

public Label setText(String newText) {     // source-compatible with every caller today
    if (text.isLiteral() && text.get().equals(newText)) {
        return this;                       // no allocation for a status label re-set per frame
    }
    return setText(I18nString.literal(newText));
}

public String text() { return text.get(); }     // signature unchanged
public I18nString textSource() { return text; } // for whoever wants the key back
```

That allocation guard matters: `Label.setText`'s existing comment explains that a ticking
status label must not full-flash the window (`Label.java:102-105`), and a wrapper allocated
per frame would be a new cost on exactly that path.

Same conversion, same shape: `Button.text` (`Button.java:35,98,102`), `TextField.placeholder`
(`TextField.java:46,100,425-427`), `TabbedPane.addTab(String, …)` and `TabHeader.title`
(`TabbedPane.java:112,116,630,638`), ColorPicker's channel labels and `Format` tabs
(`ColorPicker.java:191,214,989-991`), `Viewport3D`'s fallback message (`:256`).

**`SearchField` is the proof this design is the right one.** Its whole revision-1
workaround (a flag, an attach subscription, an override of `setPlaceholder`) collapses to
what it always was:

```java
private static final I18nString PLACEHOLDER =
        new I18nString("limn.searchField.placeholder", "Search…");

public SearchField() {
    setPlaceholder(PLACEHOLDER);           // an app's setPlaceholder("Buscar") just replaces it
    ...
}
```

`Theme.name` stays an identifier (it is API); `Theme.displayName()` returns an `I18nString`
built as `limn.theme.<kebab-name>` with the identifier as its English.

### 2.4 `limn-components`: `Spinner.java` (formats, not strings)

Display, measurement and parse move **together**: `format()` is already shared so measure
cannot drift from paint (`Spinner.java:260-264`), and parse's javadoc owns the separator
tolerance this section must preserve (`:419-422`). The widget keeps a `DecimalFormat`
validated against `I18n.epoch()`, exactly as `I18nString` keeps a string: same mechanism,
different payload.

Display formats with `DecimalFormatSymbols.getInstance(I18n.locale())`: locale decimal
separator, grouping **off**, ASCII digits kept, `RoundingMode.HALF_UP` pinned (DecimalFormat
defaults to HALF_EVEN; `%.Nf` rounds ties up today, `:269`). Parse is a normalization layer
**then** `NumberFormat` with `ParsePosition` and a full-consumption check. The normalization
keeps every tolerance users already have and NumberFormat alone would drop: a leading `+` is
stripped (the regex at `:106` and `acceptsChar` both admit it; DecimalFormat has no positive
prefix), the existing unambiguous-separator tolerance survives (`1,5` under en-US still reads
1.5, the concession parse's own javadoc defends), and the ASCII hyphen is normalized to the
locale minus (sv-SE formats U+2212; keyboards type U+002D, so without this, no negative number
could ever be committed there). `acceptsChar` (`:453`) admits the locale's separator and both
minus forms. Full consumption is what kills the de-DE `1.234` → 1.234 misread. Grouping stays
off and digits stay ASCII so the width argument at `:617-621` (extremes bound every value)
keeps holding. Commit failure stops being a silent drop (`:392`): the editor reverts with a
brief themed flash; once formats widen per-locale, the unexplained no-op would dominate the
failure budget. Time mode stays hard 24h `HH:MM`: 12h/AM-PM is pattern-driven segment
*geometry* (`:674-691,848`), not a format string, and is deferred. The AltGr exemption
(`:880`, how de-DE/ABNT layouts type digits and commas) is load-bearing and must survive.

SpinnerTest pins the locale: assertions like `"0.50"` and `"07:30"`
(`SpinnerTest.java:138,144`) run under a fixed test locale, and tests that call `setLocale`
reset it; process-wide statics leak across tests, the same tradeoff Fonts already made.

### 2.5 `limn-backend-lwjgl`: `LwjglDisplay.java`

One string, and it is the parameterized one (`:53`):

```java
private static final I18nString FALLBACK_NAME =
        new I18nString("limn.display.fallbackName", "Display {0}");
...
return name != null && !name.isBlank()
        ? name
        : FALLBACK_NAME.format(Integer.toString(index + 1));
```

The argument is pre-formatted on purpose: MessageFormat would otherwise number-format it
under the locale, producing `"Display 1,000"`, or digits the pipeline cannot draw (§4).

### 2.6 Tests and tooling: what `declaredKeys()` buys

```java
@Test void everyDeclaredKeyIsTranslated() {
    ComponentStringsProbe.instantiateEveryComponent();          // populates the registry
    Map<String, String> declared = I18n.declaredKeys();
    Properties ptBr = load("/i18n/limn_pt-BR.properties");
    assertEquals(Set.of(), Sets.difference(declared.keySet(), ptBr.stringPropertyNames()));
}
```

Coverage equals what the probe instantiates: an honest limit, and a much smaller hole than
a document nobody updates. The same map dumps a starter `.properties` for a translator, in
declaration order, with the English as the value.

### 2.7 Async bundles: documented recipe, no new code

`Ui.async(() -> PropertyBundle.of(locale, download(locale))).thenAccept(I18n::addBundle)`:
the worker loads, the UI thread folds in, `addBundle` bumps and notifies, every scene
relayouts and every `I18nString` re-resolves on its next read. It is the shape by which
background-loaded CJK faces already cure `.notdef` boxes (`FontStore.java:124-129`).

### 2.8 The demo

A locale ComboBox beside the theme picker, a `--locale` flag beside `--control-size`, one
real bundle (pt-BR) split across two files so the multi-file path is exercised, and a locale
axis on the screenshot harness.

## 3. Cost

**Runtime.** A resolved read is a `long` compare and a field read. A language change costs
one relayout (identical to a font-family switch, already accepted) plus one hash get per
distinct string per registered bundle, paid once, then cached. With no bundles registered
at all, `resolve` returns the English immediately and the UI is byte-for-byte what it is
today.

**Memory.** Three fields per distinct localizable string, plus the declared-key map (one
entry per key, bounded by the catalog, which is the point). Components declare their
strings `static final`, so widget instances carry a reference, not a copy.

**API.** Four public types, one interface method, and one added overload per existing text
setter. Nothing is removed and no signature changes: `setText(String)` and `String text()`
keep working, which is what makes this landable in one pass rather than a migration.

## 4. What this deliberately is not

- **Not BiDi/RTL.** No reordering stage exists and caret/selection/hit-testing assume
  monotone LTR (`TextField.java:289`); layout has no direction concept either: Flex places
  children in order at an increasing cursor, `Keys.LEFT` means "previous"
  (`SegmentedControl.java:220-224`), chevrons point one way. Mirroring is a toolkit-wide ADR
  of its own. Safe to defer because `I18nString` is direction-blind: an RTL locale's bundle
  is just strings; what changes later is rendering and layout, not the type.
- **Not shaping.** Arabic joining, Indic conjuncts, emoji ZWJ need GSUB, structurally
  blocked by the code-point-keyed atlas (`GlyphAtlas.java:109`). No Arabic/Hebrew/Indic/Thai
  fallback faces are added before shaping exists: unshaped text is wrong text.
- **Not locale-aware line breaking, collation or segmentation.** Label wraps on ASCII space
  with per-code-point hard breaks (the only way unspaced CJK wraps today, with no kinsoku);
  the one collation site is the font-family `TreeSet` under `CASE_INSENSITIVE_ORDER`
  (`FontStore.java:83`), exposed but not consumed in-repo.
- **Not plural rules, not per-subtree locale.** One process-wide locale: two windows in two
  languages is impossible in v1. The escape hatch is known and shaped: the ControlSize
  inheritance chain (`ControlSize.java:25-28`). *Per-subtree locale since delivered by ADR 035,
  in exactly that shape; plural rules still out.*
- **Not 12h time, not non-ASCII digits, not Unicode normalization, not localized shortcut
  labels** (`glfwGetKeyName` is never called today). Each is recorded here so its later
  absence reads as a decision, not an oversight. *Non-ASCII digits have since been closed by
  ADR 033*; the rest stand.

## 5. Risks and open edges

- **The trap moved rather than vanished.** `label.setText(someI18nString.get())` still
  captures, but it is now an explicit unwrapping, visible at review, instead of the
  default spelling. The remaining internal risk is a *component* that resolves into a
  private cache; the epoch is the tool for that, and `TextArea`'s widest-line cache
  (`TextArea.java:306`) is the known one to convert.
- **`static final` constants are class-initialization-ordered.** A component's strings
  register when its class first loads, so `declaredKeys()` before that returns less than the
  full catalog. The parity test's probe exists precisely to force loading; a tool dumping
  the catalog must do the same, and the ADR states it rather than letting someone discover
  an empty file.
- **N bundles × misses.** Every unresolved key walks all registered bundles before falling
  back to English. Once per string per switch, so it is bounded, but an application with a
  hundred files and a typo'd key pays that walk on every language change, silently. A
  debug hook that logs unresolved keys once each is cheap insurance; not in v1. *Still not in
  (2026-09-03); the item is carried in `docs/design/i18n.md`'s "Not yet" list, which is where the
  i18n backlog lives now, so this document is no longer the place to look for it.* *In since
  2026-09-26 as `I18n.observeUnresolvedKeys`, a listener, with a once-per-key log when nobody
  listens; `docs/design/i18n.md` says what counts as a miss.*
- **String expansion.** German captions run long; no fixed pixel widths exist in the
  text-bearing components (survey grep negative) and Spinner's width bound survives
  grouping-off ASCII digits, so the risk is application-level, noted in the demo bundle as
  living documentation.
- **Normalization is unexamined.** IME commits and macOS paths can deliver NFD;
  `TextEditModel` compares raw strings and no `java.text.Normalizer` use exists. V1 changes
  nothing; flagged for the day a bug report arrives with é≠é. *Still unexamined (2026-09-03), and
  carried in the same "Not yet" list.*
- **When an accessibility API lands, its labels are `I18nString`s.** Deciding that now costs
  one sentence and avoids a second retrofit.

## 6. Work plan

1. **`limn.i18n` + tests**: `I18nString`'s epoch cache, literal identity, `I18n`'s
   prepare→bump→notify order, `PropertyBundle`'s locale fallback chain, `declaredKeys`.
   Nothing renders differently.
2. **Scene subscription and its two cleanup sites** (§2.2), plus converting `TextArea`'s
   private cache to epoch validation.
3. **The one-field conversion** across Label, Button, TextField, TabbedPane, ColorPicker,
   Viewport3D, SearchField, `Theme.displayName()`, `LwjglDisplay`, and the two `Locale.ROOT`
   fixes in the backend. This is the step where "no existing caller changes" is proven by
   the suite going green untouched.
4. **`Spinner`**: display/parse/acceptsChar together, revert flash, pinned-locale tests.
5. **The catalog test and the dump tool** (§2.6).
6. **Demo**: locale picker, `--locale`, a two-file pt-BR bundle, locale-flip screenshot.

Steps 1–2 are invisible; step 3 is where the source-compatibility claim becomes verifiable;
steps 4–6 are where a pt-BR user first sees a comma and a translator first sees a file.

## 7. Open questions

- **Should `I18nString` be exposed on every setter, or only on components with declared
  strings?** This ADR says every text-bearing setter, because an application's `Label` is
  the most common place a localized string lands. The alternative (`I18nString` only inside
  the toolkit) would make applications write `label.setText(s.get())` and re-invent the
  capture bug the type exists to prevent.

## 9. What the implementation settled (deltas from the text above)

- **§2.4 is the one part not delivered.** Spinner still displays and parses under
  `Locale.US`. The specification above stands and is worth keeping, because a decimal
  separator is a behavior change with its own test-pinning work
  (`SpinnerTest.java:138,144` assert `"0.50"` and `"07:30"` verbatim), and shipping it
  alongside a mechanism change would have made one bisect two features. Everything
  else in §2 is in. *Delivered on 2026-09-27, as its own change; §9.1 records how.*
- **Chinese needed an inference the ADR never mentioned.** Translations are filed
  under `zh-Hans`/`zh-Hant`; machines report `zh-CN`/`zh-TW`. Without deriving the
  script from the region, every Chinese user would have fallen through to English (the
  one place where the region alone picks between two written forms that do not
  substitute for each other). `PropertyBundle.script()` is deliberately that small.
- **A domain does not need a file per language, and saying so is part of the design.**
  The colour picker ships French only: RVB/TSV/CMJN is a real renaming, and every
  other shipped language reads RGB/HSV/CMYK as symbols. The fallback chain makes
  "no file" the correct way to say "this language does not differ here".
- **The catalog test is shaped differently than §2.6 assumed.** "Every declared key is
  translated" is the wrong assertion once ten of thirteen theme names are proper
  nouns. What is asserted instead: no shipped file names a key nobody declares, and
  every locale of a domain carries the same keys as its siblings. Both catch the real
  failures (a typo, a rename, a half-finished language) without demanding that a
  palette called Draculite be translated.
- **`ComboBox` needed a static factory.** `ComboBox(List<String>)` and
  `ComboBox(List<I18nString>)` erase to one signature, so localized items arrive as
  `ComboBox.localized(...)`. It earns its place: the demo's own theme picker is
  exactly the case, and built from `String` it would have shown yesterday's language
  after a switch (the capture bug, in the one component the ADR had not converted).
- **The conversion reached further than §2.3 listed.** `Checkbox`, `RadioButton`,
  `MenuItem`/`Menu`, `Dialog` (title, message and both button kinds) and `ComboBox`
  took the same one-field treatment, because an application's chrome lands in those as
  often as in `Label`.
- **The source-compatibility claim held.** The 934 tests that existed before this work
  passed untouched; the 30 added are the mechanism's own.
- **Hindi renders as empty boxes: verified, not predicted.** Captured from the demo
  under `--locale hi`. It ships anyway: the translation is right and the gap is one
  layer down. Arabic and Hebrew are not shipped, because they need bidi as well as
  shaping and a file would promise what two layers cannot deliver.

### 9.1 What the Spinner work settled (2026-09-27)

§2.4 is in: the spinner writes and reads a number in the language in effect, measures its box
with the same format, and flashes a refused commit instead of dropping it. `SpinnerLocaleTest`
holds each behaviour below; ten of its eighteen cases failed on the code before the change, and
the other eight are guards for tolerances and rounding that had to survive it. Where the
implementation departs from §2.4's text, it is because the toolkit moved underneath it:

- **Digits are the locale's, not ASCII.** §2.4 said "ASCII digits kept"; ADR 033 has since made
  the spinner write the active numbering system's digits, and that stays. The format writes ASCII
  and `I18n.localizeDigits` applies the system, so a declared `setNumberingSystem` still wins over
  the locale; the parse folds every known system's digits first, as before. The width argument
  still holds, because it never rested on ASCII: it rests on grouping being off and on one
  system's digits sharing an advance, which it assumed already.
- **The separators follow the digits.** The symbols are asked for with the toolkit's numbering
  system named on the locale (`-u-nu-latn`, `-u-nu-arab`, …), not for the bare locale, because
  the JDK's default digits for a language are not always CLDR's current ones as `NumberingSystem`
  holds them: JDK 21 answers Arabic-Indic digits and `٫` for bare `ar`, where the toolkit writes
  Latin, and the bare locale would have put the Arabic separator between Latin digits (`1٫5`).
  With the system named, `ar` writes `-1.5` and `ar-EG` writes `-١٫٥`, and a deployment that
  declares a system gets the separator that goes with it. `NumberFormats` follows the same rule
  through the same helper (`limn.i18n.internal.NumberLocale`, 2026-09-27), which names the system
  only where the JDK's own digits for the locale differ, because naming it where they already
  agree makes JDK 21 answer a point for Serbian in Bosnia (`sr-BA-u-nu-latn`, and the legacy
  `sr-CS`), whose decimal is a comma.
- **The minus sign is one character.** CLDR's minus for Hebrew, Arabic and Persian carries a
  direction mark (U+200E or U+061C); the spinner takes `DecimalFormatSymbols.getMinusSign()`,
  which leaves the mark out. The mark would have moved where ADR 032 pinned the sign of a
  negative value in a right-to-left form, and put an invisible caret stop into the editor.
  Swedish, Finnish, Norwegian, Estonian, Lithuanian, Slovenian, Basque and Persian write U+2212.
- **Rounding keeps `%.Nf`'s answers exactly.** `HALF_UP` is pinned as specified, and the value is
  handed to the format as `BigDecimal.valueOf(v)`, the shortest decimal that names the double:
  `%.2f` rounded that decimal, so `1.005` read `1.01`, where a `DecimalFormat` rounding the double
  itself reads `1.00`.
- **The format is cached on a `LanguageWitness`, not on the epoch alone.** Since ADR 035 a
  subtree's locale moves without the epoch; the witness is the pair the display memo already used.
- **German `1.234` is refused, not read as 1234.** §2.4 left the choice open. Full consumption
  with grouping off implies refusal: `.` is not a character a grouping-off German format reads.
  Reading 1234 would need grouping on for the parse, and the JDK's parse does not check where
  group separators sit (JDK 21 has no strict mode), so it would also read `1.5` as 15, `12.34.5`
  as 12345: the commonest slip in the language, a point typed for a decimal, silently multiplied
  by ten. The parse's own character check refuses the point before the `NumberFormat` sees it,
  and full consumption would refuse it there.
- **The tolerance, restated for a display that is not always a point.** In a text holding no
  decimal separator of the locale's own, a comma stands for one (the English tolerance §2.4 kept,
  and why it still applies where English groups with commas), the Arabic separator U+066B stands
  for one (it never means anything else, which makes it the separator's counterpart of accepting
  every system's digits), and a point stands for one wherever the locale does not group with
  points: French, Swedish, Russian, Polish, Arabic, but not German, Portuguese, Spanish, Italian,
  Dutch or Turkish. A leading `+` is dropped, and a leading hyphen or U+2212 becomes the locale's
  minus. What may follow the sign is only ASCII digits and the locale's separator, which keeps the
  old regex's narrowness: `DecimalFormat.parse` also reads `1E3`, `∞` and `NaN`, and a paste could
  deliver any of them.
- **`acceptsChar` admits more than the locale writes.** Both separators, U+066B, `+`, both minus
  forms and the locale's own separator and minus pass in every locale, because a character refused
  at the keyboard is dropped without a trace: filtering the point out of German `1.5` would have
  committed 15. The commit decides.
- **The revert flash is the border.** It lerps to `Theme.danger()`, the colour `TextField`'s
  `ERROR` state and `DateField`'s invalid border already use, snaps to full on a refused commit
  and eases in back to nothing over 0.5 s, from a private constant as the blink and hold timings
  are. Only the colour moves, so every stroke stays a declared pen. Enter, focus loss and the
  arrow press that commits first all flash; Escape and an accepted commit do not; an emptied
  field is refused like any other text, since a spinner always holds a number.
- **A reader hears nothing at a refused commit.** The accessible node carries the committed value
  and never carried the typed text, and a refused `SET_VALUE` text is already silent by test, so
  this follows the widget's own rule. Speaking the refusal is an open decision, not an oversight:
  it needs a new catalog string translated into every shipped language and a live reader run to
  know what each platform does with it.
- **`SET_VALUE` reads in the spinner's own language.** The action runs inside the widget's locale
  scope, so a German subtree in an English interface publishes `2,5` and reads `2,5` back, and
  refuses `1.234` as the editor does (`SpinnerAccessibilityTest`).
- **Unchanged, as specified:** time mode's 24-hour `HH:MM` face (only its digits localize) and
  the AltGr exemption, both now held by tests under German. `SpinnerTest` pins English, and
  `NeutralBaseShapingTest` pins it around the one case that draws a negative value.
