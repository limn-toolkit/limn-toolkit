# Internationalization

Background for `limn.i18n`: `I18nString`, `I18n`, `PropertyBundle`, what the toolkit itself ships
translated, and which scripts the text pipeline can actually draw.

Limn's user-visible text is carried as a value, not resolved at the point of use. A component stores
an `I18nString`; a language change re-lays-out every scene and each string re-resolves on its next
read. Nothing subscribes, so nothing leaks and nothing goes stale. The reasoning and the alternatives
weighed are in [ADR 006](../adr/006-i18n.md); how an *application* uses it is the published guide,
`site/src/guides/text-and-languages.md`. The locale itself is an inherited widget axis — a subtree
can hold its own language ([ADR 035](../adr/035-the-locale-is-a-property-of-the-subtree.md)); see
below.

## How a bundle resolves

A family is `base.properties` plus one file per language tag, merged least-specific first (`base`,
then `_pt`, then `_pt-BR`), so a regional file carries only what it changes. There is no limit on
families and a miss costs one hash lookup.

**Loading is lazy, and only the languages in use are resident.** A domain's bundle is registered by
its holder class's static block, so a screen nobody opens reads no file at all. A registered bundle
holds one table per language something is reading — the process locale, plus each locale a subtree
[declares](#a-subtree-can-hold-its-own-language), counted by `I18n.retainLocale`/`releaseLocale` —
and a switch or a last release drops what nothing reads: a process that has visited ten languages
holds the tables for the ones on screen, not ten. Coming back to a dropped language re-reads its
file, which happens inside `prepare` at the switch or the retain and never on a paint path. Same
rule as fonts: memory is what you are using, not what you might use.

Toolkit strings are ordinary keys and **the most recently registered bundle wins**, which is what
lets an application override anything the toolkit says without forking it.

`I18n.declaredKeys()` returns every key declared so far with its English: the catalog as a runtime
fact rather than a maintained list. It only sees classes that have been loaded, so a caller touches
the components it cares about first.

## A subtree can hold its own language

The locale is the third inherited widget axis, resolved exactly as `ControlSize` and
`LayoutDirection` are: `widget.setLocale(...)` declares for a subtree, `scene.setLocale(...)` for
a window, the host link carries it into popups and dialogs, and the chain bottoms out in
`I18n.processLocale()`. This is ADR 006 §4's escape hatch, delivered by
[ADR 035](../adr/035-the-locale-is-a-property-of-the-subtree.md); the recorded case is a Hebrew
interface holding an English, left-to-right code pane — one declaration per axis, because language
and direction genuinely vary separately.

What makes it reach existing code unchanged is the **scope**: while the toolkit measures, lays
out, paints or dispatches an event to a widget, `I18n.locale()` answers that widget's effective
locale. `I18nString.get()`, `format`, `I18n.localizeDigits`, a chart's format lambda and the
line-breaking `BreakIterator` all read the language at the moment they resolve, so the default
spelling follows the subtree with no per-widget seam to remember — ADR 006 finding 5's argument,
applied again. Outside any pass, `I18n.locale()` is the process locale, and `I18n.pushScope` is
public for the caller who needs a subtree's answer from out there.

## What ships with the toolkit

Four domains, split by what owns them:

| Domain | Module | Keys |
| --- | --- | --- |
| `/limn/i18n/components` | limn-toolkit | search placeholder, 3D-unavailable message |
| `/limn/i18n/colorpicker` | limn-toolkit | notations and channel letters |
| `/limn/i18n/theme` | limn-toolkit | palette display names |
| `/limn/i18n/display` | limn-backend-lwjgl | monitor fallback name |
| `/i18n/kitchen` | limn-demo | every string the Kitchen Sink shows |

21 locales: **pt-BR, pt, es, fr, de, it, nl, pl, cs, tr, ru, uk, id, vi, ja, ko, zh-Hans, zh-Hant,
hi, ar, he**.

Two things about that list are deliberate rather than unfinished:

- **The colour picker ships French only.** RGB, HSV and CMYK are read as symbols in every other
  language here, and French is the one that renames them (RVB, TSV, CMJN, with channel letters to
  match). Translating the acronyms elsewhere would be a mistake, not thoroughness. So the other
  languages have no file and fall back.
- **Only three theme names are translated.** `Light`, `Dark` and `High Contrast` are descriptions;
  Darkling, Draculite, Nordic, Arch Dark, Onyx Dark, Monoko Pro, Grovebox and GitHub are the names of
  the palettes they came from and read the same everywhere. All thirteen are still keys, so an
  application that disagrees can override them.

`Theme.name` stays the identifier because it is a public field other code compares.
`Theme.displayName()` is the localized one.

### Chinese

Translations are filed under `zh-Hans` and `zh-Hant`, but a machine reports `zh-CN` or `zh-TW`.
`PropertyBundle` infers the script from the region (CN/SG/MY → Hans, TW/HK/MO → Hant) so both find
their file. It is the only such inference: no other language in reach of the text pipeline splits
this way, and a general likely-subtags table is ICU's job.

## What renders today

Text is **shaped** before it is drawn: `java.text.Bidi` decides the order, HarfBuzz decides which
glyphs and where, and stb_truetype rasterizes the ones HarfBuzz chose (ADR 031). A language is
readable when a resident face covers its script, rather than only when its script needs nothing done
to it.

| | Renders | Face |
| --- | --- | --- |
| Latin, Greek, Cyrillic | ✅ | Roboto, four styles |
| CJK (ja, ko, zh) | ✅ | Noto Sans CJK, loaded in the background on first need |
| Vietnamese | ✅ | Latin with stacked diacritics, precomposed |
| Hindi (Devanagari) | ✅ | Noto Sans Devanagari: conjuncts, and pre-base matra reordering |
| Arabic, Hebrew | ✅ | Noto Sans Arabic and Noto Sans Hebrew: joining forms, marks placed by GPOS |
| Thai | ✅ | Noto Sans Thai, and `BreakIterator` under a Thai locale for the wrapping |

Hindi is the row that used to say no, and it was shipped anyway while it drew empty boxes. The two
properties that prove it draws now are pinned by tests rather than looked at once, because neither is
something a per-code-point pipeline could produce at any level of effort: `क्ष` is three code points
and exactly one glyph, and in `हिन्दी` the i-matra is drawn **before** the consonant it follows in
the string.

**Two things take that away, and both degrade rather than fail.** Where the HarfBuzz native cannot
load, every run falls back to the per-code-point walk it replaced: Latin, Greek, Cyrillic and CJK
come out at exactly the widths they had before any shaping existed, kerning included and the
f-ligatures gone; the order stays right because `java.text.Bidi` needs no native at all; and the
four complex scripts lose their joining, their conjuncts and their mark attachment. And the four
script faces are an artifact, `limn-fonts-noto-scripts`, versioned with the fonts and declared by the
backend (ADR 036), so a classpath assembled without it has nothing to draw them with and gets
`.notdef` boxes in the right order. Same contract as the decoder: a missing native, or a missing
face, narrows what the toolkit can do and never stops it.

**Every string is shaped, whichever widget draws it.** A widget whose text a caret or a hit test has
to point into holds a shaped line and asks it every geometric question; a widget that hands the
canvas a bare `String` — a button, a tab, a menu item, a placeholder — gets the same shaping, done
by the canvas through the installed ruler, and the same arithmetic again when it measures. So a
screen is joined and ordered throughout or in neither half, and "does this widget shape?" is not a
question about a locale's readability. What holding a value still buys is the geometry and the
per-frame cost, and why it is one pipeline rather than two is [text-shaping.md](text-shaping.md).

**The layout mirrors too, as its own axis.** This file used to record that `ar` and `he` had the
text and not the layout; ADR 032 closed that: alignment, scrollbars, popups, arrow keys and the
rest follow a per-subtree `LayoutDirection`, deliberately *not* derived from the locale — a Hebrew
interface holding a left-to-right code pane is one declaration on each axis. The axis itself is
[direction-axis.md](direction-axis.md).

Capture any of it:

```bash
./gradlew :limn-demo:run --args="--screenshot /tmp/fr.png --scene colorpicker-light --locale fr"
```

The kitchen sink has a language picker beside the theme and size ones, and its own strings are
translated into all 21: menu bar, tabs, buttons, labels, dialogs and status messages. The scenes it
hosts inside those tabs (the 3D viewport, the colour picker, animations, files…) are still English:
they are separate demo files, keyed the same way when someone wants them.

## Not yet

- **`Spinner`'s number entry is still `Locale.US`**: a decimal point everywhere, and a comma
  accepted only when no point is present. ADR 006 §2.4 specifies the fix (locale separator, a
  normalization layer that keeps today's tolerances, the sv-SE minus sign, a revert flash instead of
  a silent drop); it is a behaviour change with its own test-pinning work.
- **No plural rules.** Separate keys chosen by application code, until the shape of a general
  solution is worth committing to.
- **No collation.** Two of the three items that used to share this line moved: locale-aware line
  breaking landed with ADR 031 (`BreakIterator` under the UI language wraps unspaced CJK and
  dictionary-segmented Thai), and mirrored layout landed with ADR 032. Collation and case mapping
  are unchanged from ADR 006 §4.
